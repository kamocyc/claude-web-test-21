# 都市開発シミュレーション

日本を舞台にしたエージェントベースの都市シミュレーションゲーム（TypeScript + Three.js）。

市民を 1 人ひとり個別にシミュレートします。各市民は年齢・職業・学歴・所得・交通手段の好みを持ち、
自宅から職場へ通勤し、買い物やレジャーに出かけます。どの交通手段で行くかは、
実際に経路探索した所要時間・運賃・その人固有の好みから多項ロジットで決まります。

**公共交通は路線で作ります。** 停留所を順にクリックしてバス路線・電車の路線を引き、
運行間隔を決めます。バスは道路を走るので渋滞に巻き込まれ、遅れれば乗る人が減ります。

産業は田んぼと林業を起点としたサプライチェーンを持ち、
トラックが市民と同じ道路網を走って資材を運びます。

```
npm install
npm run dev          # ブラウザで遊ぶ
npm test             # テスト一式（146 件）
npm run sim:headless -- --days 180   # 描画なしでシミュレーションだけ回す
```

## 遊び方

起動すると 2 つの入口が出ます。

- **何もない土地から始める（チュートリアル付き）** — 道路 1 本から街をつくります
- **できあがった街を見る** — 仕組みが動いているところをすぐ眺めたいとき

できあがった街は**中心市街地とベッドタウン**の 2 つでできていて、住むところは
ベッドタウンに、働くところは中心市街地に寄せてあります。だから朝夕に
2 つを結ぶ**幹線道路と鉄道**へ人が集中します。幹線はわざと片側 1 車線にしてあるので、
朝 7〜9 時に交通量オーバーレイを見ると赤くなり、交差点の手前に車列が伸びます。
二車線・大通りに広げると捌けます。**ここがこのゲームの一番の見どころです。**

電気もぎりぎりの水準にしてあります。統計パネルの「電気・水道」を見ると
電力が 100% すれすれで、街が育つとすぐ足りなくなります。発電所を足すか、
成長が止まるのを眺めるかはプレイヤ次第です
（**供給が足りない地区には新しい建物が建ちません**）。

### 画面

Cities: Skylines の配置に寄せてあります。

| 位置 | 内容 |
|---|---|
| 左上 | 都市名・人口・資金・**月次収支**・幸福度・失業率／日時と時間速度 |
| 右上 | マイルストーン（人口で解禁されるもの） |
| 下中央 | ツールバー（カテゴリを選ぶと道具が上に出る） |
| 右下 | RCI 需要バー（住・商・工・農）と情報表示の切替 |
| 左 | 選んだ市民・建物の詳細 |
| 左下 | チュートリアル |

| 操作 | |
|---|---|
| 画面移動 | Alt + ドラッグ / WASD / 矢印キー（いずれもカメラの向き基準） |
| 回転 | 右ドラッグ / Q・E |
| ズーム | ホイール |
| 時間速度 | 1〜4 キー、スペースで一時停止 |
| 選択解除 | Esc |
| 保存・読込 | 左上パネルのボタン |

時間速度は **×1 / ×4 / ×20** で、1 日がそれぞれ実時間 32 分 / 8 分 / 1.6 分です。
×1 は街を眺めるための速度で、人も車も電車も現実的な速さに見えます。
発展させたいときは早送りしてください（早送り中は当然その分だけ速く見えます）。

道具はカーソル横に費用と可否（「ここには敷けません」など）が出ます。
ドラッグ中は敷かれる範囲が地面に光り、**敷けないマスだけ赤**になります
（斜面・水面・既存の建物）。建物は 1×1 とは限らないので、置く前に占有する範囲が出ます。

### 近景に映るもの

ズームインすると、街に人と車両が出ます。

| | いつ出るか |
|---|---|
| 歩行者・自転車 | カメラ距離 460m 未満。移動中の人は経路上を実際に進む。屋外に立たせるのは**買い物中とレジャー中だけ**（在宅・勤務・通学は屋内にいる扱い） |
| 自家用車（走行中） | 車で移動中の市民。左側通行で車線に寄せて走る |
| 自家用車（駐車） | カメラ距離 900m 未満。車を持つ市民の車を、その人が今いる場所（車で来ていなければ自宅）の路肩に停める |
| トラック | 物流のトラック。**積荷ごとに色が違う**ので、何がどこへ流れているかが街を見るだけで分かる。帰路は空車色 |
| バス | 路線を走る。**車体は路線の色**なので、目の前を通ったのがどの系統か分かる。道が詰まれば車と一緒に止まる |
| 電車 | 線路の上を 3 両編成が往復する（先頭車だけ色が濃い）。駅が 1 つも無い線路には走らない |

車両はどれも**車体・窓・屋根・車輪の部品でできています**。トラックは運転台と荷台に分かれ、
バスは窓の帯が高い位置に回り、電車には床下機器・台車・冷房・パンタグラフが載っています。
**夜は前照灯と尾灯が点き、バスと電車は車内灯が窓 1 枚ずつ灯ります**。

道路も描かれます。車道・歩道・センターライン・停止線・横断歩道・一方通行の矢印があり、
市街地の歩道には街路樹と電柱が並びます。建物は切妻・寄棟・陸屋根で作り分けてあり、
**夜になると窓が灯ります**（棟と階でばらしてあるので、全部が一斉に光ることはありません）。

線路はバラスト・枕木・レール 2 本・架線柱でできています。踏切ではバラストの代わりに
踏切板が敷かれ、四隅に警報機が立ちます。

街の外側も平らではありません。森林には杉と雑木が茂り、山地には岩が転がり、
田んぼは畦で区切られます。**木の色は季節で変わり**、冬の高山は雪をかぶります。

駐車中の車を描いているのは、車の大半が 1 日のほとんどを停まって過ごすからです。
走行中だけだと、街に映る自家用車が実態よりずっと少なくなります。

### マイルストーン

人口が増えるにつれて道具が解禁されます。最初から全部渡されても何をすればいいか分からないので、
「次に何ができるようになるか」が街を育てる動機になるようにしてあります。

| 人口 | 呼称 | 解禁 |
|---|---|---|
| 0 | 開拓地 | 生活道路・低層住居・畑・公園・役所 |
| 40 | 集落 | 近隣商業・水田・林業・交番 |
| 150 | 村 | 二車線道路・準工業・学校・**太陽光発電所・浄水場** |
| 400 | 町 | **鉄道・駅**・消防署・中高層住居・下水処理場 |
| 1,000 | 市 | 大通り・商業地域・工業地域・病院・神社・**火力発電所** |
| 3,000 | 中核市 | オフィスビルが建つ |
| 6,000 | 中核都市 | タワーマンションが建つ |

### チュートリアル（全 11 段階）

説明を読ませるのではなく、街の状態を見て達成したら次に進みます。
道路 → **電気と水** → 用途地域 → 住民 → 職場 → お店 → 食料の自給 → 公共施設 → 鉄道 → 木材の自給、
という順にこのゲームの因果関係をひととおり体験できます。

電気と水が 2 番目なのは、**供給が足りない地区には新しい建物が建たない**ためです。
道路を引いた直後に発電所と浄水場を建てておかないと、最初の 1 軒から先へ進みません。

**確認しておくと面白いところ**

- **近景で住民と車両が見えます** — カメラを寄せると、通りに人が立ち、通勤時間帯には歩道を歩きます。
  路肩には自家用車が並び、トラックが積荷の色で走り、線路の上を電車が往復します（すべて実寸）。
- **市民インスペクタ** — 「選択」ツールで市民をクリックすると、その人の年齢・職業・自宅・職場・
  今日の行程に加えて、**直近の交通手段選択の内訳**（各手段の所要時間・運賃・選択確率）が出ます。
  「1 人ひとりをシミュレートしている」ことがその場で確認できます。
- **経路確認ツール** — 2 点をクリックすると、その間の経路探索結果が地図上に赤い線で描かれます。
  道路を 1 タイル壊してからもう一度試すと、迂回路に切り替わります。
- **建物インスペクタ** — 工場や商店をクリックすると、在庫・**現在の仕入先**・欠品日数が見えます。
  物流が滞っている原因を追えます。
- **情報表示** — 地価・交通量・用途地域・公害・交通アクセス・**電力・上水道**をヒートマップで
  重ねられます。交通量だけは色が数分ごとに追従するので、朝夕のラッシュに赤くなって昼に引くのが見えます。
- **路線を引く** — 「路線」ツールで停留所を順にクリックし、Enter で確定します。
  バス路線なら道路の上、電車なら駅をつないでいきます（最後の停留所をもう一度クリックしても確定します）。統計パネルに系統数・車両数・
  今日の乗車回数が出て、月々の運行費が収支に乗ります。
- **道路の混雑** — 統計パネルに「走行中の車両 / 信号待ち・渋滞 / 詰まっている道路 / 所要時間の倍率」が出ます。
  詰まりがひどくなると場所つきで通知します。

## 設計

### レイヤ

```
src/sim/     シミュレーション本体。three.js も DOM も一切参照しない
src/render/  three.js による描画。sim を読むだけで、書き換えない
src/ui/      日本語 UI。sim には Command を発行するだけ
src/app/     3 者を配線してゲームループを回す
```

`sim` が描画から完全に独立しているので、Node 上でそのままテストでき、ヘッドレスで
何百日分でも回せます。テストの 146 件はすべてブラウザなしで動きます。

プレイヤ操作はすべてシリアライズ可能な `Command` として表現し、tick 境界でのみ適用します。
シード＋コマンド列があれば同じ街が再現できるため、決定論テスト・セーブデータ・
不具合の再現手順が同じ仕組みから得られます。

### 1 万人を個別に動かすための仕掛け

素直に作ると必ず性能の壁にぶつかる箇所が 3 つあり、それぞれ対策を設計に埋め込んであります。

**1. 毎 tick 全市民をループしない — タイミングホイール**

各市民は「次に何かが起きる tick」だけを持ち、その tick のバケツに入ります
（`sim/core/timeWheel.ts`）。1 人あたり 1 日 6〜10 イベント（起床・出発・到着・退勤・買い物・帰宅）
なので、1 万人でも **1 tick あたり平均 50〜70 件**しか処理しません。
在宅中・勤務中の市民は文字通りゼロコストです。

ホイールから予約を個別に取り消す仕組みは持たず、**起床時に `wakeTick` と照合して古い予約を捨てます**
（遅延削除）。これが無いと静かに壊れます。就職・転居のたびに予約を取り直していたため、
市民が予約を二重に持ち、1 日のステップを 2 倍速で消化して時計と位相がずれていました。
一度ずれると戻らないので、**2030 人中 1466 人がずれ、会社員の 9 割が深夜 23 時に出勤する街**に
なっていました。画面上は「夜なのに車が多い」だけで、朝夕のラッシュが存在しませんでした。

**2. 意思決定に経路探索を使わない — TAZ コスト行列**

「どこで働くか」「どこで買い物するか」「どの交通手段にするか」「どの工場から仕入れるか」は
所要時間の概算しか必要としません。ゾーン間のコスト行列（`sim/network/tazMatrix.ts`）を
ローリング更新しておき、これらの判断は配列参照 1 回で済ませます。
実際の A* が要るのは「本当に移動する経路が必要」なときだけです。

**3. 経路キャッシュと探索予算**

キャッシュのキーは建物ではなく**道路ノード**です。40 世帯のマンションも 200 人のオフィスも
接道点は 1 つなので、ヒット率が跳ね上がります（人口 7,000 の街で実測 98.8%）。
容量は 12 万件。ここが足りないと追い出しが常時起きてヒット率が 75% まで落ち、
1 tick の処理時間が 1.3ms まで悪化します（実際に踏みました）。
さらに 1 tick あたりのノード展開数に上限を設け、溢れた市民は「出発準備」状態で待たせます。
プレイヤが幹線道路を撤去した瞬間に全市民が一斉に再探索してフレームが飛ぶ、という事故を防ぎます。

**重要な規約: 混雑ではキャッシュを捨てません。** キャッシュしているのは「経路」であって
「所要時間」ではありません。混雑で無効化すると、交通量が最大のまさにその瞬間に
キャッシュが全滅して探索が爆発します。

### 1 日のトリップと朝夕のラッシュ

市民は生活パターンのテンプレート（`sim/agents/schedules.ts`）を 1 つ持ち、
そこに **ID から決まる固定のジッタ**を足した時刻に動きます。ジッタが固定なのは、
毎日同じ人が同じ時刻に同じ経路を通ることで経路キャッシュが効くからです。

- 会社員（8:00 出勤 / 13:00 業務移動 / 18:30 買い物 / 19:30 レジャー / 20:30 帰宅）
- 早番（6:30 出勤 / 16:00 買い物 / 17:00 帰宅）、夜勤（21:30 出勤 / 6:30 帰宅）
- 学生・主婦主夫・高齢者・無職

**寄り道を「しない」と決めたときに、その場に留めるのが要点です。**
以前はここで自宅に `settleAt` していました。すると勤務先にいる市民が自宅に瞬間移動し、
**帰宅トリップそのものが発生しません**。会社員は買い物 40%・レジャー 25% で寄り道するので、
両方外した 4 割強が夕方に職場から消えて家に湧いていて、夕ラッシュが半分になっていました。
症状は「夕方なのに道路が空いている」だけなので、これは統計を見ないと気付けません。

同じ種類の見落としがもう 1 つあり、`ScheduleKind.ShiftWorker` はテンプレートが
書かれているのに `pickSchedule` に分岐が無く、一度も割り当てられていませんでした。

### 交通手段の選択

各手段の所要時間・運賃・駐車探索時間を体感分に換算し、多項ロジットで確率的に選びます。

```
GC_m = 体感所要分 + 運賃 / 時間価値 + 駐車探索分
U_m  = -GC_m + モード固有定数 + その人の好み + 目的別バイアス
P(m) = exp(U_m/θ) / Σ exp(U_k/θ)
```

- 好みは市民ごとに生成時に一度だけ引き、生涯変わりません
- 時間価値は所得に比例します（金持ちほど時間を金で買う）
- 自動車は 18 歳以上かつ保有者のみ、鉄道は両端が駅の徒歩圏にある場合のみ
- 都心ほど駐車探索時間が長く、自動車が不利になります
- **定期券**を持つ勤め人は通勤の鉄道運賃が 0 になり、鉄道分担率を強く押し上げます

argmax ではなく確率的に引くのが要点です。同条件の市民が全員同じ選択をすると、
交通量が全か無かで振れて街が壊れて見えます。分担「率」として出したいので抽選します。

### 渋滞 — 車が場所を占めて、信号で止まる

集計式ではなく、**車両 1 台ずつが道路上の場所を占め、前の車を追い越せず、
交差点の信号で止まる**モデルです（`sim/network/traffic.ts`）。渋滞は結果として出ます。
所要時間は予測しません。**着いたときが到着時刻です。**

有向リンクごとに待ち行列を持ち、先頭の車は次の 4 つを全部満たしたときだけ次のリンクへ出ます。

1. リンクに入ってから**自由流時間**が経っている（道路種別の速度で決まる）
2. **飽和交通流率**の枠が空いている（1 車線 1800 台/時。行列ができて初めて効く制約）
3. 下流の交差点の信号が**青**である
4. 次のリンクに**空きがある** ← これが上流へ伸びる渋滞（spillback）

これで「車間」「信号待ち」「追い越し不可」「渋滞の伝播」が全部出ます。
加速度の連続的な表現だけがありません（後述の縮尺の理由で、そこまで刻む意味がないため）。

#### 画面の車 1 台 = 実車およそ 9 台の車列

**この定数を知らずに交通の数字をいじると、渋滞が全域に出るか一切出ないかのどちらかになります。**

人口 2000 の街では、朝ラッシュに最も混む道でも 1 時間に 33 台しか通りません。
生活道路の実容量 600 台/時 に対して 5% で、実車 1 台 = 1 エージェントとして
車間を取らせても行列は一生できません。

一方、地図は **1/15 縮尺**（`TILE_SPAN_M` / `TILE_M`）で、車は 4.2m で描かれています。
この車 1 台が地図上で占める実距離は 63m ＝ 実車 9 台分の車列にあたります。
そこで「画面の車 1 台 = 実車およそ 9 台の車列」と定義し直すと、
**縮尺のデフォルメと台数のデフォルメが `VEHICLE_PLATOON` ひとつに集約されて**数字が噛み合います。

| | 値 | 根拠 |
|---|---|---|
| 車列 1 台の長さ | 65m | 描画の車長 4.2m × 15 |
| 1 リンク（150m）の収容 | 2 台 | 150 ÷ 65。車線数を掛ける |
| 交差点の飽和交通流率 | 200 台列/時 | 実車 1800 ÷ 9 |
| 青が半分なら 1 方向の容量 | 約 100 台列/時 | |
| 実測のピーク需要（最混雑リンク） | 33〜100 台列/時 | |

つまり**最混雑の数本だけが飽和し、残りは自由流**になります。

#### 信号

道路リンクが 3 本以上集まるノードに自動で置きます。直線の途中と行き止まりには置きません。
**位相はサブステップ数とノード番号だけの純関数**なので、信号は状態を持たず、
セーブにも復元にも何も要りません。

**青の配分は道路種別で決めます。** 大通り側に長い青を与えるので、
生活道路を二車線・大通りに広げると「捌ける台数」と「溜められる台数」が同時に増え、行列が引きます。
これがプレイヤの持つ操作レバーです。

#### 1 tick を 12 分割する

1 tick = 1 分のままだと、車は 1 分に 1 リンク（150m）しか進めず時速 9km になってしまいます。
5 秒刻みで解くことで、自由流なら 1 分に 3〜4 リンク進み、信号も 60 秒周期という現実的な値で書けます。

#### 経路探索へのフィードバック

車がリンクを抜けるたびに**実測の通過時間**を記録し、EMA で平滑化して `edgeCarSec` に流し込みます。
信号待ちも spillback も、この 1 つの数字に入ります。A* が読むのは今までどおりこれだけです。
平滑化が無いと「混む → 全員迂回 → 迂回路が混む」の発振が確実に起きます。
しばらく車が通らなくなったリンクは自由流へ戻します（そうしないと、一度混んだ道が
誰も通らなくなったまま「混んでいる」と記録され続けます）。

さらに市民ごとに ±5% の固定的なコスト摂動を掛け、等コストの並行路へ流れを分散させます。

#### 位置を持つのは車両だけ

シミュレーションは原則として位置を持たず、`(経路, 出発 tick, 到着 tick)` から描画時に復元します。
**車両だけが例外で、`(リンク, そのリンクに入った時刻)` を持ちます。** 信号待ちの車は
停止線の手前に車列 1 台ぶんずつ下がって並ぶので、そのまま描けば行列に見えます。
歩行者・自転車・電車は互いに干渉しないので、従来どおりの補間のままです。

**車は 1 tick に平均 3.8 リンク（最大 6）＝ 560m 進みます。** 今いるリンクしか持たないと、
描画は毎 tick「4 マス瞬間移動 → 停止線でじっと待つ」しか描けません。
そこで直近のリンク乗り換えを 8 件だけ覚えておき、tick の中の任意の時刻について
**そのとき本当にいた場所**を返します。1 tick を平均して滑らかにする手もありますが、
信号の 1 周期が 60 秒 ＝ ちょうど 1 tick なので、それだと赤で止まっている様子が完全に消えます。

描画する時刻は**直前に計算し終えた tick の中**をなぞります（`clock.tick - 1 + 端数`）。
`clock.tick` は tick の最後に加算されるので、素直に `clock.tick + 端数` と書くと
まだ計算していない未来を指してしまい、端数 0 の瞬間から既に終端に着いていることになります。

#### グリッドロック

閉路上の全リンクが満杯になると永久に止まります。既知の失敗モードなので逃がし弁を入れてあります。
十分待った車は満杯のリンクにも 1 台だけ押し込み、それでも 8 時間かかったトリップは打ち切ります。
`test/traffic.test.ts` の「容量の何倍を流し込んでもデッドロックしない」がこれを守っています。

### サプライチェーンと物流

```
田んぼ ──米──┐
              ├─→ 食品工場 ──食品──→ 商店・コンビニ・スーパー ──→ 市民の買い物
畑     ──野菜─┘

林業区画 ──原木──→ 製材所 ──木材──┬─→ 建物の建設が消費（街の成長速度を律速する）
                                    └─→ 町工場・工場 ──日用品──→ 商店
```

- 水田は **9 月に一年分がまとめて穫れます**。倉庫の必要性と、毎年決まった時期の物流の山が生まれます
- 消費側の在庫が減ると発注し、供給元からトラックが出ます。トラックは市民と同じ道路グラフを A* で走り、
  **同じ交通流に載ります**。交差点で信号待ちし、乗用車 2.5 台ぶんの枠を食い、帰りの空車も道路を占めます。
  工場を市街地の反対側に置けば、その物流が実際に通勤路を詰まらせます
- 発注の判定には**輸送中の数量**を含めます。ここは移動が一瞬だった頃は害が出ませんでしたが、
  交通流を入れて配送が実時間を食うようになった途端、到着するまで同じ店に発注し続けて
  トラックが際限なく増え、資源地への道が空車と実車で恒久的に詰まりました（走行 626 台中 571 台がトラック）
- 仕入先は一度決めたら固定します（取引関係）。毎回選び直すと OD ペアが毎回変わって
  経路キャッシュが効かず、配送そのものが成立しなくなります
- 地元に木材が無い場合は輸入で賄えますが高くつきます。林業〜製材所を整備すると建設費が下がります

### 街が発展する仕組み

- **接道していない区画には絶対に建物が建ちません。** これが道路設計をゲームにする一番の要です
- 魅力度 = f(地価, **鉄道アクセス**, サービス到達, 平坦さ, 公害, 騒音)。
  鉄道アクセスの重みを地価に次ぐ大きさにしてあるのは意図的で、
  「駅を先に敷いて周りをゾーニングしたプレイヤが報われる」ようにするためです（私鉄の沿線開発）
- 建設確率は魅力度の 2 乗に比例します。良い場所から順に埋まり、条件の悪い土地は
  圧力が高まるまで空いたままになります。線形にすると全域が一様に埋まってのっぺりした街になります
- タワーマンションやオフィスビルは市の人口が一定を超えてから出現します
- **中高層住居ゾーンには 1×1・1×2・2×2 の 3 サイズを用意してあります。**
  以前は 2×2 のマンションしか無かったため、6×6 の街区の内側 5×5 にマンションが 4 棟しか入らず、
  L 字の 9 タイルが永久に空いていました。「中密度を密集させた」のに実際には密にならない、
  という食い違いが街区あたり人口を 4 割ほど押し下げていました

### 転入と建設は別の信号で決める

ここは一度間違えて、**人口が永久に 0 のまま**になった箇所です。

「空き家が多い」は *これ以上家を建てるな* という信号であって、*人が引っ越して来るな*
という信号ではありません。むしろ空き家があるからこそ移り住めます。
両方を住宅需要ひとつで判定していたため、

```
家が建つ → 全部空き家 → 住宅需要がマイナス → 誰も転入しない → 永久に空き家
```

というデッドロックに入っていました。いまは分けてあります。

- **建設**は RCI 需要（空き家が多ければ下がる）
- **転入**は「空き住戸があるか」＋「街が住むに値するか」（求人の余り・幸福度・税率）

### 業種は「原料が地元で手に入るか」で選ばれる

同じ種類のデッドロックがサプライチェーンにもありました。

- 原材料不足の工場が多いと工業需要を下げていたが、それでは**不足を解消する当の製材所**
  まで建たなくなる → 抑制はするが止めない強さに調整
- 品薄の資源を作る業種を優先するが、**原料が地元で手に入らない業種は逆に抑える**。
  これが無いと、木材が 1 単位も無い段階で町工場が準工業地を埋め尽くし、
  そのあと全部休止して食品工場の入る余地が消えます
- 「不足していない」だけでは判定できません。誰も欲しがっていない資源は不足量が 0 に
  見えるだけなので、**在庫か生産があるか**まで見ます
- 区画の隅に残った 1 マスを埋める小さい建物へのフォールバックにも同じ判定を効かせます。
  効かせないと、1×1 の町工場が区画を分断して 2×2 の食品工場・製材所が
  どこにも入らなくなります

### 距離と時計のスケール — 地図は 1/15 で描いている

`TILE_M = 10` は 1 タイルの**描画上の**大きさ、`TILE_SPAN_M = 150` は
1 タイルが**シミュレーション上で表す実距離**です。この 2 つを分けているのは、
次の 2 つを同時に成り立たせるためです。

1. 1 日が実用的な長さで進む
2. 人・車・電車が現実的な速さに見える

この 2 つは 1 本の式で結ばれていて、両立できる組み合わせは限られています。

```
1 日の実時間（分） = 19152 ÷ （歩行者の見た目の速さ[m/s] × 1 タイルの実距離[m]）
```

10m/タイルのままだと、歩行者が歩く速さに見える時計では 1 日が実時間 8 時間になり、
逆に 1 日を 2 分にすると時間が実時間の 720 倍で流れ、**電車が地図を 0.2 秒で横断**します。
150m にして初めて、1 日 32 分と現実的な速度が同時に成り立ちます。

副次的に、これまで意味を成していなかった距離がすべて現実的になりました。

| | 変更前 | 変更後 |
|---|---|---|
| 平均通勤時間 | 3 分 | 26〜39 分 |
| 駅の徒歩圏 | 120m | 1.2km |
| 自転車の上限距離 8km | 地図全体が 3.2km で**一度も効かない** | 実際に効く |
| 同時に移動している市民（人口 2000） | 4 人 | **平均 93 人・最大 733 人** |

最後の行が「街が生きて見える」かどうかを決めます。実在の都市でも移動中の人は
人口の 5% 程度で、変更前の 0.3% は距離が短すぎたせいでした。

**単位を跨ぐ箇所には必ず `SIM_PER_RENDER` を掛けること。** 特に
`Graph.straightLineM()` は A* のヒューリスティックに使われるので、掛け忘れると
ヒューリスティックが非許容になり、**A* が黙って最短でない経路を返します**。
症状は「車が変な道を通る」だけで目視では追えません。
`test/pathfinding.test.ts` の「A* の結果がダイクストラと一致する」が唯一の検出手段です。

この変更で `transitAccess`（駅までの徒歩分）が 15 倍になり、
以前は街じゅうで「徒歩 3 分」だったものが本来の値に戻りました。
その結果、地価と魅力度に常時乗っていた鉄道ボーナスが駅の近くだけに戻り、
街全体がレベルアップ閾値を下回って人口が固定されました。
地価と魅力度の基礎値でその分を補ってあります
（鉄道は人口 400 で解禁されるので、鉄道が無くても成長できる下限は必ず要る）。

### 経済の時間だけデフォルメする

距離と時計を作り直した結果、1 日は実時間 2 分から **32 分**になりました。
移動の見た目はこれで正しくなりますが、**経済側は「1 日単位」で回ったまま**なので、
実時間で見ると転入も求職も建設判定も 16 倍遅くなります。
プレイヤから見ると「家を建てても 30 分誰も来ない」「商店を建てても就業者が 0 のまま」で、
ゲームが壊れているようにしか見えません。

1 日の長さと移動の見た目は変えずに、**経済の時間だけ**デフォルメして取り戻します。

| | 周期 | ×1 での実時間 |
|---|---|---|
| 転入・求職・雇用統計・収支 | `ECONOMY_PERIOD_TICKS` = 120 tick（2 時間） | 2.7 分 |
| 地価・サービス圏 | 日次 ＋ **プレイヤが建てた／壊した瞬間** | 即時 |
| 公害・在庫切れ・廃業・レベルアップ・加齢・出生・転居 | 日次 | 32 分 |
| 決算 | 月次 | 16 時間 |

加速するのは「**建つ・育つ・来る・雇われる**」側だけです。
廃墟化・廃業・転出の猶予日数は据え置いてあります。破壊側まで速めると、
サプライチェーンが立ち上がる前に上流が全滅する事故が起きます（実際に起きました）。

一時停止中もコマンドは適用します（`Simulation.flushCommands()`）。
`applyCommands()` が `tick()` の先頭にしか無かった頃は、停止して道路を引いても
道路が現れず、課金もされず、警告も出ませんでした。停止して街を作るのは普通の遊び方です。

求職まわりで直したものがもう 2 つあります。どちらも「就業者が 0 のまま」の原因でした。

- 求職は「市民 1 人につき 7 日に 1 回」でした。×1 では 3.7 実時間に 1 回です。
  回転カーソルで未就業者を一巡させる方式に変え、2 時間ごとに回します
- `seekJob` は TAZ 行列のコストが `Infinity` のとき**黙って候補を捨てて**いました。
  行列は 1 周 200 tick かけて埋まるので、街を作り始めた直後は採用が一切成立しません。
  移動側と同じ直線距離のフォールバックを入れ、`bootstrap()` で行列を先に埋めます

### 公共交通は「路線」でできている

バスも鉄道も、プレイヤが**停留所を順に指定して引いた路線**の上を走ります。
路線は停留所の並び・運行間隔・種別（バス／電車）を持ち、運行間隔を縮めると
必要な車両数と月々の運行費が増えます。

グラフには路線ごとに**プラットフォーム・ノード**を置き、3 種類のエッジを張ります。

| エッジ | コスト |
|---|---|
| 乗車（停留所 → プラットフォーム） | 乗車ペナルティ ＋ 運行間隔/2 × 待ち時間重み ＋ 混雑ペナルティ |
| 乗車中（プラットフォーム間） | 区間の実所要 ＋ 停車時間 |
| 降車（プラットフォーム → 停留所） | 降車ペナルティ |

路線が違えばプラットフォームも別なので、**乗換は「降りて歩いて乗る」として
自然に表現されます** — 待ち時間をもう一度払うだけで、乗換の重さが正しく値付けされます。
モードは増やしていません。`Mode.Transit`（公共交通）1 つでバスと鉄道の両方を指すので、
1 回のトリップの中で「バスで駅まで出て電車に乗り継ぐ」が経路探索の結果として出てきます。

**バスは道路の渋滞に巻き込まれます。** 区間の所要は、その区間の道路リンクについて
交通流が実測した通過時間の合計です。しかもバス車両自体が `TrafficSystem` に載って
車列の一部として場所を占有するので、道が詰まればバスも遅れ、遅れれば分担率が落ち、
車がさらに増えます。専用軌道を走る電車はこの影響を受けません
—— **路線の種別を分けている理由はここにあります。**

区間ごとの乗車人数も数えていて、輸送力（定員 × 60/運行間隔）を超えたぶんは
待ち時間に上乗せされます（＝積み残し）。「増発する」という判断に意味が出ます。

線路と駅だけを置いた場合は、**駅が 2 つ以上ある線路の連結成分に路線が自動生成されます。**
線路を敷いたのに何も走らない、という状態を作らないためです
（自動路線は保存せず、線路と駅から作り直します）。

線路は分岐（次数 3 以上）で切って別の線として扱います。跨いで 1 本に繋ぐと、
電車が分岐点で不自然に折り返します。

### 電気と水道は道路の下を通っている

専用の管路網は敷かせません。**供給は道路網の連結成分を伝わります。**
CS の電線・水道管をこの規模（320×320 タイル）に持ち込むと、操作が煩雑になる割に
意思決定が「繋いだかどうか」しか生みません。日本の実情（道路占用で埋設する）にも
近い割り切りです。

- 発電所・浄水場・下水処理場を建て、道路で繋がった地区に供給が届く
- 建物は接道タイルでどの地区に属するかが決まる
- 足りなければ**建物スロットの昇順で打ち切る**（乱数で落とすと、
  同じセーブから同じ街にならないうえ、毎期ちがう建物がちらついて原因が読めない）
- 2 日続けて落ちた建物は機能停止し、生産が止まって住民の幸福度が下がる
- **供給が足りない地区には新しい建物が建たない。** これが無いと、
  上限を超えても街が伸び続けて不足がどこまでも広がり、放っておくと必ず崩壊します。
  建設の側で止めれば、街は供給の天井で自然に伸び止まり、発電所を足した分だけまた伸びます
- 浄水場は取水できる水辺（1.2km 以内）にしか建ちません
- 下水処理が足りない地区は、その分だけ公害が上がります

道路で繋がった地区には、**既存の系統から 2,400kW / 1,400m³ が無条件で届きます。**
日本の町は最初から電力会社と水道本管に繋がっていて、ゼロから始めると
「道路 1 本の開拓地がいきなり発電所を建てないと全戸停電する」という
遊びづらさだけが残るためです。人口 4,000 前後で足りなくなります。

### 一方通行は「逆走だけ」を禁じる

交通モデルは元から有向リンクの待ち行列なので、入れ物を足すだけで効きます。
タイルごとに向きを持ち、`Graph.build()` で**指定の真逆に出る車のエッジだけ**を落とします。
「指定の向きに出るときだけ通す」という条件にすると、一方通行の途中から脇道へ
曲がることまで塞がれて、入ったら最後まで抜けられない道になります。
歩行者と自転車は常に双方向です（歩行者に一方通行はありません）。

信号は交差点の次数から決まるので、一方通行にすると青の配分も自動的に変わります。

### 乗り物は「今どのエッジにいるか」で描き分ける

自動車の経路は両端に徒歩区間を含み（駐車して歩く）、鉄道の経路は両端に駅までの
徒歩区間を含みます。モードだけで見た目を決めると、**車が歩道を走り、電車が線路を降りて
歩道を歩きます**（実際にそうなっていました）。

`pathPosition()` が現在いるエッジの index を返すので、`edgeMask` を見て
車道なら車、線路なら（車内にいるので）描かない、それ以外は歩行者、と切り替えます。
おかげで「駅まで歩く鉄道利用者」が初めて描かれるようになりました。

### 地面の上に置くものを増やしても重くならない作り

木は 4 万本を超えます。他の描画レイヤと同じ「1 種類 1 メッシュ・`frustumCulled = false`」で
置くと、カメラを最大まで寄せていても毎フレーム 4 万本ぶんの頂点処理が走ります。
実際、素朴に置いた時点で 1 フレームの時間が 3 倍以上に伸びました。
効いたのは次の 2 つです。

**マップを 64 タイル角の区画に切り、区画ごとにメッシュを持つ。**
こうすると three.js が区画単位で「画面に入っていない」を判定して丸ごと捨ててくれます。
街に寄っているときは 25 区画のうち 1〜2 区画しか処理されません。

**木の色をジオメトリに焼き込む。**
`instanceColor` で色を変えようとすると、幹と樹冠を別メッシュに分けるほかなくなり、
インスタンス数が倍（幹 4 万 ＋ 樹冠 4 万）になります。色は季節ごとに数種類しか無いので、
種類ぶんのジオメトリを作って頂点色に焼いてしまえば、幹と樹冠が 1 インスタンスで済みます。
季節が変わったときだけジオメトリを作り直します。

車両でも同じ手を使っていますが、こちらは逆向きです。**頂点色を絶対色ではなく
変調係数として持たせ**（車体 = 白、窓 = 暗い灰、タイヤ = ほぼ黒）、
`instanceColor` に車体色を入れます。three.js は `頂点色 × instanceColor` を掛けるので、
**色を 1 つ差し替えるだけで窓もタイヤも一緒に付いてきます** —
白い車の窓は明るい灰に、黒い車の窓は真っ黒に。1 台 1 インスタンスのままです。

### フィードバックループ

このゲームが「動いている」と言えるのは、プレイヤの操作が痛みや報酬として返ってくるからです。

```
道路設計が悪い → トラックが届かない → 商店の在庫が切れる
  → 市民の買い物が失敗して不満が溜まる → 転居、それでも駄目なら転出
  → 地価が下がる → 建物が廃墟になる → 税収が減る

学校・病院・交番・公園を届かせない → 幸福度が下がり続ける（基礎値はマイナス）
工場が原材料不足で止まっている → 工業需要が下がり、それ以上工場が建たなくなる
林業と製材所が足りない → 木材が輸入頼みになり、建設費がかさむ
```

需要モデルの全項は容量で正規化して範囲を clamp してあります。素の比を使うと、
この手の経済は指数的に発散するか、逆に過減衰して人口数千人で永久に止まります。

### セーブデータ — 作り直せるものは保存しない

状態はほぼ全部が SoA の TypedArray なので、JSON にせず**そのままバイト列**にします
（`sim/persistence.ts`）。人口 2000 の街で約 1.4MB。JSON にすると 20 倍以上に膨らみます。

保存しないものが 3 つあります。いずれも他の状態から作り直せるもので、
保存すると形式が複雑になるうえ、古いセーブデータと実装の食い違いを生みます。

| 保存しないもの | 復元のしかた |
|---|---|
| 地形（標高・傾斜・水系） | シードから再生成する。決定論なので 1 ビットも変わらない |
| 交通グラフ・TAZ 行列・経路キャッシュ・タイミングホイール | 読み込み後に作り直す |
| 走行中の経路（市民のトリップ・トラックの配送） | 作り直せないので**打ち切る**。市民は自宅に戻し、トラックは荷を降ろす |

3 つめだけは情報の損失です。読み込むと、そのとき移動中だった数十人が自宅からやり直します
（スケジュールの進行位置は保つので、生活のリズムは崩れません）。
経路は節点番号への参照であり、読み込み後のグラフでは別の場所を指すので、
そのまま走らせると存在しない道路の上を走ることになります。

置き場所は **IndexedDB とファイルの両方**です。localStorage は使いません。
1.4MB を文字列にすると base64 で 1.9MB になり、多くのブラウザの上限 5MB に対して
街が育つと**保存した瞬間に静かに失敗する**ためです。

読み込みではシードごと差し替わるので `Simulation` を作り直します。描画側は毎フレーム
`sim` を引数で受け取る作りなので、キャッシュを捨てさせるだけで済みます。

### 斜めから見たときのカーソル

画面座標からタイルを求めるとき、高さ 0 の平面と交差させるだけでは**手前にずれます**。
標高 20m の丘を仰角 40°から見ると、見えている地面と高さ 0 の交点は
20 / tan(40°) ≒ 24m ＝ 2 タイル以上離れるためです。

「今の推定高さの水平面と交差 → その位置の標高を読む」を数回繰り返して収束させています
（`Renderer.pickTile`）。斜面が視線より急でなければ 2〜3 回で止まります。

## 既知の制約と次の一手

- 路線に時刻表はありません。運行間隔だけを持ち、待ち時間は「運行間隔 ÷ 2」で値付けします
  （ダイヤを持たせても、乗客が時刻表を見て家を出るモデルにしない限り結果は変わりません）
- 交通グラフは道路タイル 1 枚 = 1 ノードです。この規模（数千ノード）ではキャッシュと
  探索予算で十分に収まりますが、10 万人規模に伸ばすならセグメント縮約が最初の最適化対象です
- `sim` が描画から完全に独立しているので、Web Worker への移行は
  アロケータの差し替えで済む設計になっています（v1 ではデバッグしやすさを優先してメインスレッド）
- 港湾・貨物駅による輸出入、災害、観光客の流入、地区と条例は未実装です
- 近景の住民は、移動中の人は経路上を実際に歩きます。屋外に立たせるのは買い物中と
  レジャー中だけで、在宅・勤務・通学中の人は屋内にいる扱いにして描いていません
  （以前は全員を玄関前に立たせていて、位置が ID から決まる固定値なので
  「同じ人が一日じゅう同じ場所に立ち尽くす街」になっていました）
- 電車の描画は路線の折れ線を端から端へ往復するだけで、駅で止まって見えるわけではありません
  （所要時間の側には停車時間が入っています）。バスは交通流に載っているので実際に止まります
- 増発は自動ではありません。混雑は待ち時間として経路コストに出ますが、
  運行間隔を縮めるかどうかはプレイヤの判断です
- 電気・水道に「送電ロス」や「水圧」はありません。道路で繋がっていれば地区の端まで同じように届きます
- 一方通行は車だけに効きます。バスも同じ制約を受けるので、
  一方通行の環状路にバス路線を引くと片方向だけ極端に遠回りになります
- 自動車の経路は徒歩の区間を通れる設計（駐車して歩く）なので、**迂回路が 1 本も無いとき**は
  一方通行の逆走区間を「歩いて」通り抜けます。迂回できる街ではきちんと迂回します
- 地図は 1/15 スケールで描いています。1 タイルは実距離 150m の街区で、そこに建つ
  1 棟の箱は街区 1 つ分を表します。建物 1 棟あたりの収容人数は実距離に合わせて
  上げていないので、シミュレーション上の人口密度は実際の日本の市街地より低めです
  （交通量の側は `VEHICLE_PLATOON` でこの差を吸収しています）
- 早送り（×4・×20）中は、時計が速い分だけ人も車も電車も速く見えます。
  見た目とシミュレーションが完全に一致するのは ×1 のときだけです
- 車両の相互作用は待ち行列モデルです。車間・信号待ち・追い越し不可・渋滞の伝播は出ますが、
  加速度と減速度は表現していません（1 台が実車 9 台の車列を表す縮尺なので、
  数 m 単位の車間を積分しても意味がないため）。右左折の分離現示もありません
- 走行中の経路変更はしません。渋滞は出発前の経路選択にだけ効きます
  （車がどのノードにいるかは分かっているので、足すこと自体は難しくありません）
- 道路を 1 タイルでも編集すると、走行中の車は全部降りて自宅からやり直します。
  経路が節点番号への参照なので、グラフを作り直すと別の場所を指してしまうためです
- 渋滞の状態はセーブしません。読み込み直後の道は空いていて、1 時間ほどで元に戻ります。
  走行中のバスも同じで、次の tick から配車し直します
- 建物インスペクタの選択は世代タグ付きのハンドルで持っていますが、**市民の選択は生 ID のまま**です。
  選択した市民が死亡して同じスロットが再利用されると、別人を表示し続けます
  （市民ストアに世代タグがないため。足すならセーブ形式の変更を伴います）
- 経済の反応速度は実時間基準に取り直してありますが、需要（RCI）の再計算だけは
  日次のままです。在庫切れ判定など「日数を数える」処理と入力を共有しているためで、
  需要バーが動くのは 1 日に 1 回です
- 業務移動の行き先は雇用のある事業所からの重力モデル抽選で、取引関係は見ていません
- セーブデータを読み込むと、そのとき移動中だった市民のトリップは打ち切られます
  （数十人が自宅からやり直す）。セーブデータの形式が変わったら、古いファイルは
  読み込まずにエラーにします（`SAVE_FORMAT_VERSION`）
- ブラウザ内のセーブは 1 枠だけです。複数の街を残したいときはファイルに保存してください
